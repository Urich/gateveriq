# Deployment and configuration

## Local testing

Run the README quick start first. Defaults expose both listeners only on localhost. Build output remains local. This project does not publish binaries, containers or releases.

Run under a dedicated unprivileged account. On Unix use `umask 077` before initialization and ensure only the service account can read/write the database directory. SQLite sidecar files contain sensitive metadata too.

Configuration paths generated by `init` are absolute. Override the config location using the global flag **before** the subcommand:

```sh
gateveriq --config /etc/gateveriq/config.toml serve
```

| Key | Default | Meaning |
|---|---|---|
| database | Absolute local path | SQLite database |
| token_key_file | Absolute local path | Canonical Base64URL key, 32 random bytes |
| public_listen | 127.0.0.1:9080 | Public routes and widget assets |
| internal_listen | 127.0.0.1:9081 | Loopback-only server API |
| difficulty_bits | 18 | Deployment-wide difficulty, allowed 1–24 |
| challenge_ttl_seconds | 120 | Allowed 10–600 |
| token_ttl_seconds | 60 | Allowed 10–300 |
| retention_seconds | 300 | Receipt retry window and cleanup retention, allowed 300–86400 |
| requests_per_minute | 120 | Fixed-window limit per bucket |
| max_active_challenges | 1000 | Per-integration cap on unexpired challenges |

Configuration is loaded at startup. Changes require restart. Existing challenge difficulty/expiry remain unchanged. The key file contains only the key, with an optional trailing newline.

## Reverse proxy

Example Caddy configuration inside an existing HTTPS site block:

```caddyfile
handle_path /gateveriq/* {
    reverse_proxy 127.0.0.1:9080
}
```

Never forward the internal listener. Assets are `/widget.js` and `/worker.js`; no demo application is served at `/`.

The service deliberately ignores forwarded-IP headers. Behind a proxy, its IP limit groups clients under the proxy address. Apply real-client per-IP limits at your trusted ingress and size the service limit for aggregate traffic. Do not expose the public listener directly to the internet before configuring ingress limits, TLS and resource controls.

## Integration administration

```sh
gateveriq integration-create --name forum --actions signup,comment
gateveriq integration-rotate --id INTEGRATION_ID --grace-seconds 300
gateveriq integration-disable --id INTEGRATION_ID
gateveriq cleanup
```

Rotation prints a new secret once; the previous secret works until its grace deadline. Only one previous secret is supported. A second rotation replaces it. Disabled integrations cannot issue or consume; their existing public solutions may still be computed but cannot authorize an action. Re-enable and action editing are not exposed in this MVP.

## Backup and upgrades

Use SQLite's backup API or stop the service before copying the database. Back up the private token key with it and protect the backup. Copying only the main database while WAL is active is unsafe. There is one schema version; future releases must implement migrations before changing it. Do not share one database between independently deployed versions.

Token-key rotation is **not implemented** in this MVP. Replacing the key while challenges exist can break retries. For emergency rotation stop issuance and the service, expire/purge outstanding challenges, replace the key securely, and restart; clients must start new operations. Routine automatic key rotation is deferred.

## Health and operations

`GET /health` on the public listener returns `ok` as a liveness check; it does not prove database readiness. Database failures return a generic service error. Cleanup failures go to stderr without secrets. Structured metrics/audit logging, graceful draining, multi-node operation and a production service installer are deferred.
