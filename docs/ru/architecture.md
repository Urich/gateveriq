# Архитектура

[English](../architecture.md) | [Русский](architecture.md)

Сервис реализован одним Rust-пакетом. Выделение отдельно версионируемых crates
отложено до стабилизации интерфейсов.

| Компонент | Назначение |
|---|---|
| `src/core.rs` | Каноническое кодирование, SHA-256 PoW и нативное решение |
| `src/service.rs` | Задачи и токены, SQLite, авторизация, лимиты и HTTP |
| `src/website.rs` | Аккаунты, origins, результаты входа, правила риска и CORS |
| `src/visual.rs` | Картинки, смена задач, бюджет ответов и набор иллюстраций |
| `src/main.rs` | Инициализация, запуск и управление интеграциями |
| `web/widget.js` | Наблюдения, выбор картинок, отправка и отмена |
| `web/worker.js` | Вычисление PoW в браузере |
| `sdk/server.mjs` | Необязательный серверный клиент для Node.js |
| `assets/visual/tiles/` | Подготовленные картинки, встроенные в бинарный файл |
| `examples/prepare_visual.rs` | Подготовка исходных атласов вне HTTP-запросов |

## Границы доверия

Клиенту доверять нельзя. Только авторизованный сервер приложения создаёт попытки,
использует токены и сообщает результат входа. Он выбирает неизменяемую привязку
действия, контекста и аккаунта. Клиент не задаёт сложность и не сообщает результат
проверки пароля. Секреты остаются на сервере приложения.

Публичный и внутренний API работают на разных адресах прослушивания. Внутренний
API разрешён только на loopback; удалённому приложению нужен закрытый
аутентифицированный транспорт. Режим сайта проверяет точные origins и реализует
CORS. Origin не защищает от бота, способного отправлять произвольные HTTP-запросы.

## Сценарии

Исходный сценарий: подготовка → решение PoW → использование токена → выполнение
операции приложения. Проверки браузера, поведения и истории IP включаются отдельно.

Режим сайта добавляет попытку входа, связанную с аккаунтом. При риске назначается
визуальная задача. Правильный выбор и исходное PoW дают токен той же попытки.
Сайт использует токен, проверяет пароль и сообщает результат. Его собственные
сессии и транзакции должны предотвращать повторное выполнение операции.

## Хранение

SQLite использует WAL, внешние ключи и ожидание занятости до двух секунд.
Внутрипроцессный mutex сериализует транзакции. Уникальность задачи задаётся
интеграцией, действием и контекстом. SHA-256 применяется к случайным секретам
с высокой энтропией; токен восстанавливается по закрытому ключу HMAC.

Таблицы содержат интеграции, действия и origins, политики, задачи, квитанции
использования токенов, минутные счётчики, привязки аккаунтов, результаты входа
и состояние картинок. Аккаунты и IP представлены HMAC-псевдонимами.
Повтор одного результата входа идемпотентен, изменение результата отклоняется.

Неправильный выбор атомарно расходует попытку и, если бюджет остаётся, меняет
категорию, поле и ID задачи. Срок действия сохраняется. Старый ID не подходит
для нового поля, повторное получение задачи не сбрасывает бюджет. Новая попытка
исключает последнюю сохранённую категорию для того же аккаунта и интеграции.

## Очистка и границы реализации

Очистка запускается каждую минуту и удаляет до 500 подходящих строк из каждой
очищаемой таблицы. Удаление родительских задач каскадно удаляет картинки и
привязки сайта. Срок хранения квитанций и истории настраивается отдельно.
История по умолчанию хранится 24 часа. Просроченные данные перестают влиять на
риск, даже если физическое удаление задерживается. Контексты нельзя использовать
повторно после очистки.

Это прототип с одним процессом и одной БД, фиксированной сложностью PoW и
правилами проверки. Кластер, обученный классификатор, доверенные пересланные IP,
панель управления и невизуальная дополнительная проверка не реализованы.
Статический набор иллюстраций предназначен для пробы оформления.
