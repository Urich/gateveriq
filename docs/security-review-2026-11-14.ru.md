# Проверка безопасности Gateveriq 14 ноября 2026

Проверен код коммита `fd29869`, зависимости и локально запущенные API. Основные
границы доступа выдержали проверки: внутренние маршруты закрыты на публичном
порту, токены привязаны к интеграции и контексту, конкурентное погашение допускает
одного потребителя. Для публичного применения остаются риски: уязвимая зависимость
SQLite, бессрочное накопление контекстов и уже документированные ограничения
антибот-проверки.

## Статус исправлений

Введены серверные контексты с HMAC-подписью и сроком действия. Постоянная таблица
used_contexts удалена из новой схемы. Истёкший контекст отклоняется после очистки
и перезапуска. SDK и примеры используют новый API; старый формат и миграции
не поддерживаются.

Выбор категорий заменён слайдером-пазлом со случайным пейзажем и вырезом для каждой
задачи. Правильная позиция остаётся на сервере; PoW, привязка, срок и бюджет
сохранены. Старое сопоставление 24 PNG по хешам неприменимо к новому протоколу.
Устойчивость к компьютерному зрению не установлена; слайдер допускает угадывание.

Текущая проверка: 27 Rust-тестов, все пять JS-файлов, HTTP/CLI и 90 утверждений
security-сценария прошли. В Firefox проверены реальные стрелки/Enter, перетаскивание
с выдачей и погашением токена, темы и контейнер 240 px. Security-сценарий теперь
использует привилегированное чтение координаты из временной БД для проверки
протокола; это не демонстрация устойчивости к ботам.
[Параметры встраивания](ru/website-integration.md#темы-и-встраивание-слайдера).

Ниже сохранены результаты исходного аудита коммита fd29869; они описывают прежнюю
реализацию. Уязвимая SQLite-зависимость и особенности общей IP-истории этим
изменением не исправлялись.

## Уязвимая зависимость SQLite

**Средний риск, подтверждено сопоставлением версии с RustSec.** В
[Cargo.toml](../Cargo.toml#L14) включён `rusqlite` с `bundled`. Фактическая цепочка:
`gateveriq → rusqlite 0.32.1 → libsqlite3-sys 0.30.1`; встроенный SQLite имеет
версию 3.46.0.

[RUSTSEC-2026-0459](https://rustsec.org/advisories/RUSTSEC-2026-0459.html),
также CVE-2026-119375, описывает раскрытие памяти при открытии специально
подготовленных файлов БД и WAL с различными размерами страниц. Оценка RustSec —
6.8, вектор локальный. Злоумышленник должен иметь возможность подложить эти файлы;
удалённая эксплуатация через проверенные HTTP-маршруты не установлена.

Обновить `rusqlite` до совместимого выпуска, который использует
`libsqlite3-sys >= 0.39.0` и SQLite >= 3.54.0, затем проверить миграцию существующей
базы и повторить тесты. Обычный `cargo update` в пределах текущего требования
`rusqlite = "0.32"` не гарантирует такое обновление. До обновления хранить БД,
WAL и резервные копии в каталоге, доступном только пользователю сервиса.

Проверка cargo-audit использовала 1509 advisories базы RustSec, коммит
`4ef2df8e806a65e2f1ecc14f56f51249062b23d6` от 13 ноября 2026. Исключения advisories
не задавались; проверка yanked-пакетов отключена через `--no-yanked`.
Полный результат команды завершился кодом 1 из-за найденной уязвимости.

## Бессрочное накопление контекстов

**Средний риск для доступности при длительной работе или массовом создании
попыток.** [Миграция](../src/service.rs#L115) создаёт `used_contexts` без времени
истечения; каждая новая попытка [добавляет запись](../src/service.rs#L327).
[Очистка](../src/service.rs#L201) удаляет challenges и историю, но не эти записи.
Лимит `max_active_challenges` учитывает только неистёкшие challenges.

В локальном воспроизведении после удаления всех challenges осталось 8 записей
`used_contexts`. После ещё десяти созданий и второго цикла очистки challenges
снова стало 0, а `used_contexts` — 18. Для накопления записей не нужно решать PoW.

Прямая запись требует секрета внутреннего API. Удалённый пользователь сможет
ускорить рост, если backend сайта позволяет часто запрашивать новые попытки.
Ограничения частоты замедляют рост, но не задают предел общего размера базы.
Это риск накопления состояния; заполнение диска в ходе проверки не выполнялось.

Сначала ограничить создание попыток на backend по сессии, аккаунту и источнику,
задать квоту хранилища и мониторинг. Затем определить срок хранения и стратегию
архивации использованных контекстов. Простое удаление записей изменит гарантию
запрета повторного использования контекста: проект уже проверяет её тестом
`cleaned_context_cannot_be_recreated`, поэтому изменение требует согласованного
протокола с backend.

## Подтверждённые ограничения антибот защиты

### Статические картинки решаются без распознавания

**Высокий риск, если использовать текущий visual как защиту от автоматизации
в рабочей системе.** Это ограничение уже описано в [README](../README.md) и
[модели безопасности](security.md), а не новая скрытая уязвимость.

[Банк картинок](../src/visual.rs#L274) состоит из 24 неизменяемых PNG с известными
категориями. Скрипт вычислил SHA-256 файлов публичного репозитория, сопоставил их
с `reference` и `images` из ответа API и выбрал все картинки нужной категории.
Распознавание изображений, браузер и чтение поля `answer` из SQLite не потребовались.

Пять из пяти заданий решены с первой попытки. Backend успешно погасил все пять
токенов и получил `verification_method = pow_visual`. PoW при этом действительно
решался. Пять заданий показывают воспроизводимость способа, а не измеряют
устойчивость к любым ботам.

Для рабочего применения пересмотреть механизм дополнительной проверки и
проверить его против автоматического решателя. Переименование файлов и перестановка
картинок не устранят сопоставление по содержимому. Метод `pow_visual` подтверждает
прохождение текущего протокола, но не присутствие человека.

### Данные браузера можно подделать

Python-клиент получил обычный PoW-токен, отправив самостоятельно сформированные
`browser` и `behavior` с допустимыми значениями. Это соответствует заявленной
модели: эти поля являются слабыми сигналами, а не аттестацией устройства. Не
использовать их как основание обходить собственные ограничения входа, регистрации
или отправки писем.

### Общий адрес прокси объединяет историю пользователей

**Средний эксплуатационный риск за reverse proxy.**
[История](../src/service.rs#L489) использует транспортный IP; за одним прокси
разные посетители имеют общий источник. Это поведение документировано в
[развёртывании](deployment.md).

Пять запросов к legacy `/public/v1/solutions` с известным website challenge ID,
некорректным nonce и без Origin потратили бюджет ошибок. Последующая корректная
website-проверка с того же транспортного адреса получила HTTP 403 и дополнительное
визуальное задание. Токен без проверки не был выдан, полной блокировки не произошло.
Для воспроизведения нужен действующий challenge ID; его нельзя практически
угадать, но пользователь интегрирующего сайта обычно получает свой ID при подготовке.

Перенести ограничения по реальному клиенту на доверенный ingress. Если добавлять
поддержку forwarded IP, принимать такие заголовки только от явно доверенных прокси.
Также проверять website binding до изменения истории на legacy-маршруте, чтобы
запросы без подходящего origin не загрязняли website-историю этим путём.

## Проверенные защитные свойства

- Публичный порт возвращает 404 для внутренних маршрутов; обратное разделение
  также сохраняется. Публично сообщить результат входа нельзя.
- Подготовка требует аутентификации. Секрет другой интеграции не подходит;
  действие вне allowlist отклоняется.
- Подмена интеграции, контекста, аккаунта или origin отклоняется. Даже другой
  разрешённый origin нельзя подставить в уже связанную попытку.
- Из восьми конкурентных запросов с разными request ID только один погасил токен.
  Точный повтор с победившим ID проходит, новый ID отклоняется.
- Погашенный токен нельзя получить повторно через public solutions.
- Некорректный JSON, лишние поля, неверный content type и тело больше 4096 байт
  отклоняются. SQL-метасимволы в action не проходят валидацию.
- Дубли индексов и индекс 16 в visual отклоняются; неверный ответ меняет task ID,
  сохраняя deadline и бюджет. Старое задание и попытка сбросить потраченный бюджет
  отклоняются.

Поиск секретов охватывал текущие текстовые файлы и историю всех 10 доступных
коммитов. В истории проверялись сигнатуры приватных ключей, AWS access-key ID и
GitHub-токенов; в текущих файлах дополнительно искались длинные литералы
учётных данных. Это ограниченный поиск по шаблонам.

## Повторный запуск

Из корня репозитория:

```sh
cargo build --locked
python3 tests/security_audit.py
```

[Сценарий](../tests/security_audit.py) не принимает внешний адрес или чужие
credentials. Он запускает временный сервер только на loopback и завершает его
после проверки. Перевод временных challenges в истёкшее состояние выполняется
тестовым доступом к временной БД, чтобы не ждать таймеров. В актуальном сценарии правильная позиция берётся из временной БД как тестовый fixture;
описанный ниже JSON сохраняет результаты исходного аудита старого механизма. Проверки воспроизведения текущих рисков потребуется
обновить после исправлений; автоматически в CI сценарий не добавлен.

Результаты запуска и краткая сводка dependency-аудита сохранены в
[JSON](security-review-2026-11-14.results.json). Проверка не является заключением
о полной безопасности всех сценариев и развёртываний проекта.
